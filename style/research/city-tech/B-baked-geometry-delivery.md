# Baked geometry delivery for a ~940-block voxel city (three.js r185, WebGL2, no bundler)

## Recommended format and pipeline

**Ship glTF/GLB with `EXT_meshopt_compression` + `KHR_mesh_quantization`, not Draco, and not raw typed-array blobs.**

- **Meshopt over Draco.** Draco reduces raw mesh bytes further (50–80% vs meshopt's 30–60%), but meshopt decodes 5–10x faster, and community guidance is explicit: Draco wins for 1–3 hero models, meshopt wins for scenes with 50+ small meshes where decode time dominates ([svilenkovic.com/3d/draco-vs-meshopt](https://svilenkovic.com/3d/draco-vs-meshopt)). At ~940 blocks × 3 tiers, this project is squarely the "many small meshes" case.
- **Decode speed is the deciding number.** The meshopt v1 decoder exceeds 5 GB/s on Apple M4 for densely packed vertex data and is up to 30% faster than the two-year-old v0 decoder; WASM SIMD decode on desktop CPUs runs roughly ~1 GB/s ([meshoptimizer.org/v1.html](https://meshoptimizer.org/v1.html)). This is CPU/WASM work that parallelizes across workers, matching your existing worker pipeline.
- **Quantization does most of the size work.** `gltfpack` (the meshoptimizer CLI) quantizes positions to 16-bit normalized integers relative to the mesh AABB and normals to 8-bit×3 or a packed 10_10_10_2 format, with node scale absorbing the AABB range ([meshoptimizer.org/gltf](https://meshoptimizer.org/gltf/), [github.com/zeux/meshoptimizer#422](https://github.com/zeux/meshoptimizer/issues/422)). This lands inside three.js's `KHR_mesh_quantization` support, present since r111 ([meshoptimizer/gltf/README.md](https://github.com/zeux/meshoptimizer/blob/master/gltf/README.md)).
- **three.js integration is a loader flag, not a rewrite.** `GLTFLoader` has supported `EXT_meshopt_compression` since r122 via `loader.setMeshoptDecoder(MeshoptDecoder)`, where `MeshoptDecoder` ships as an ES module (`examples/jsm/libs/meshopt_decoder.module.js`) that assumes WASM support ([three.js PR #20508](https://github.com/mrdoob/three.js/pull/20508), [three.js discourse](https://discourse.threejs.org/t/unable-to-load-meshopt-compressed-glb-file-in-react-native/70180)). That module is importable straight from a CDN, fitting your no-bundler importmap setup.
- **glTF/GLB over a custom raw-binary format.** Binary glTF stores geometry attributes as typed arrays that map directly onto GPU buffers with no additional parsing — effectively zero-copy — while the JSON header is small and fast to parse with `TextDecoder` + `JSON.parse` ([Khronos glTF issue #357](https://github.com/KhronosGroup/glTF/issues/357)). A hand-rolled binary format buys little over this and costs you tooling, validators, and inspector support.
- **Textures: KTX2/Basis Universal, if/when the blocks carry texture data.** KTX2 gives 4–8x memory reduction and 4–8x faster GPU upload vs uncompressed textures, and transcodes at load time to whatever the device GPU prefers — BC7 desktop, ASTC iOS, ETC2 Android ([donmccurdy.com/2024/02/11/web-texture-formats](https://www.donmccurdy.com/2024/02/11/web-texture-formats/)). Your blocks are currently vertex-coloured (AO baked into vertices), so this mainly matters if you add tiled albedo/normal textures later — don't add texture infrastructure you don't need yet.

**Voxel-specific packing, on top of glTF quantization:** greedy-meshed voxel vertices commonly cost ~28 bytes each with position/UV as full f32; packed formats bring this to ≤16 bytes, and aggressive schemes reach 8–12 bytes by packing position, normal index, and material/texture index into a few bits each ([ft_vox #110](https://github.com/gkehren/ft_vox/issues/110), [Vercidium](https://github.com/Vercidium/voxel-mesh-generation), [voxel-nexus #94](https://github.com/PetrSeifert/voxel-nexus/issues/94)). Palette-indexed colour follows the same logic as the material-index packing above, but no source found publishes concrete byte-savings for it specifically — **treat that figure as unverified** until benchmarked against your own AO+colour data.

**Delivery mechanics:**
- Pre-compress every baked `.glb` with Brotli at build time and serve with the right `Content-Encoding`; pre-compressing avoids per-request CPU cost at the origin/CDN ([web.dev brotli codelab](https://web.dev/articles/codelab-text-compression-brotli)). Brotli typically beats gzip by ~15–20% on compressible text/JSON-adjacent payloads, and one cited real case shows a 12.4 MB payload going to 3.5 MB with Brotli vs 4.8 MB with gzip ([ioriver.io gzip-vs-brotli](https://www.ioriver.io/blog/gzip-vs-brotli-compression-performance), [Leaseweb blog](https://blog.leaseweb.com/2019/08/06/data-compression-in-online-games/)) — geometry buffers compress less dramatically than text, so measure on your own blocks.
- **Bundle blocks into a modest number of chunk files, don't ship ~2,800 tiny files (940 blocks × 3 tiers).** Compression is superadditive on larger inputs (`compress(a+b) ≤ compress(a)+compress(b)`), so one bundle compresses better than many small ones ([CSS-Tricks: Musings on HTTP/2 and Bundling](https://css-tricks.com/musings-on-http2-and-bundling/)). HTTP/1.1 pays real per-request overhead for many small files; HTTP/2 multiplexing narrows that gap but doesn't erase it. A tile-CDN case study cites batching requests down from ~15 to 2–3 per view, a ~90% request-count cut ([openstreetmap/operations #392](https://github.com/openstreetmap/operations/issues/392)). Practical shape for this project: group blocks by spatial region into a handful of bundles per tier (e.g., district-sized chunks), each independently addressable, following the general pattern of 3D Tiles' hierarchical spatial tiling streamed on demand ([Swyvl: 3D Tiles Explained](https://swyvl.io/blog/3d-tiles-explained/)).
- **Cache API over IndexedDB for the baked binaries themselves.** Cache API is purpose-built to store Request/Response pairs and bypasses IndexedDB's structured-clone/serialization overhead for binary payloads; the common real-world pattern is Cache API for static assets and IndexedDB for queryable app state ([browser-storage.com](https://www.browser-storage.com/browser-storage-fundamentals-quotas/cache-api-for-static-assets/when-to-use-cache-api-over-indexeddb/), [dev.to PWA offline storage](https://dev.to/tianyaschool/pwa-offline-storage-strategies-indexeddb-and-cache-api-3570)). This argues for migrating the current IndexedDB block cache to a service-worker-backed Cache API store for the pre-baked files, keeping IndexedDB (if at all) for small structured metadata.

## Device-tier budget table

| Tier | Signal | Notes / caveats |
|---|---|---|
| Low (older laptop iGPU) | detect-gpu tier 1 (≥15 fps benchmark) | `detect-gpu` classifies by an actual render-benchmark score, not declared specs — tier 0 = no context/blocklisted/<15fps, tier 1 ≥15fps, tier 2 ≥30fps, tier 3 ≥60fps ([pmndrs/detect-gpu](https://github.com/pmndrs/detect-gpu)) |
| Mid (Apple Silicon MacBook) | detect-gpu tier 2 | Unified memory shared between CPU/GPU; Safari/WKWebView's memory ceiling isn't fixed — depends on device RAM and system load and can crash before documented WebGL limits ([Apple Developer Forums](https://developer.apple.com/forums/thread/64909), [Wonderland Engine](https://wonderlandengine.com/news/webgl-performance-safari-apple-vision-pro/)) |
| High (discrete desktop GPU) | detect-gpu tier 3 | Historically cited VRAM spread: <1 GB (low end) to 12–24 GB (high end) ([webgl2fundamentals.org](https://webgl2fundamentals.org/webgl/lessons/webgl-cross-platform-issues.html)) — dated, treat as order-of-magnitude only, not a hard budget |

**Detect honestly, don't trust declared specs.** `navigator.deviceMemory` is Chromium-only, and values are rounded to a fixed power-of-two set and capped (historically at 8, though newer Chrome can report 16/32 on non-Android) specifically to resist fingerprinting — it is not a reliable memory budget signal ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/deviceMemory), [castle.io deep dive](https://blog.castle.io/deep-dive-how-navigator-devicememory-can-be-used-for-fingerprinting-and-bot-detection/)). `WEBGL_debug_renderer_info`'s unmasked vendor/renderer strings are useful but increasingly masked by browsers over fingerprinting concerns ([scrapfly.io WEBGL_debug_renderer_info](https://scrapfly.io/web-scraping-tools/gpu-fingerprint/webgl/webgl-debug-renderer-info)). The defensible approach is a short runtime capability probe — `detect-gpu`'s actual rendering benchmark, plus `gl.getParameter(MAX_TEXTURE_SIZE)` and similar WebGL2 limit queries — to pick tier/LOD budgets, rather than reading device metadata.

## Instancing verdict for trees (~290 woods blocks)

**Move to `InstancedMesh`.** Rendering N tree meshes individually costs N draw calls; a single-geometry `InstancedMesh` with many transforms collapses that to one draw call ([bersus.io](https://bersus.io/insights/creative-dev/threejs-optimizing-instancing-and-batching/), [threejsroadmap.com](https://threejsroadmap.com/blog/draw-calls-the-silent-killer)). Community guidance is direct: single geometry → always `InstancedMesh`; a handful (2–4) of distinct geometries → either several `InstancedMesh` or `BatchedMesh`; many distinct geometries → `BatchedMesh` is the more efficient choice ([three.js discourse: choosing between InstancedMesh and BatchedMesh](https://discourse.threejs.org/t/how-to-choose-between-instancedmesh-and-batchedmesh/81221)). If tree variety stays low (a few trunk/canopy archetypes), `InstancedMesh` per archetype is the simpler and cheaper path; reach for `BatchedMesh` only if tree variety grows into many distinct geometries, since it supports per-object frustum culling via `perObjectFrustumCulled` (default true) at the cost of more bookkeeping ([three.js BatchedMesh docs](https://threejs.org/docs/pages/BatchedMesh.html), [three.js issue #29603](https://github.com/mrdoob/three.js/issues/29603)). One caveat found in the wild: `InstancedMesh` was reported slower than plain `Mesh` in at least one heavy-per-instance-geometry case (5,000 spheres, 50 subdivisions each) despite fewer draw calls ([three.js issue #30352](https://github.com/mrdoob/three.js/issues/30352)) — keep per-tree geometry low-poly and measure rather than assume instancing is a free win.

## WebGPU verdict

**Not worth migrating for this project right now; keep tabs on it.** `WebGPURenderer` has been described as production-ready since r171 (Nov 2024) with zero-config imports and automatic WebGL2 fallback ([three.js WebGPURenderer docs](https://threejs.org/docs/pages/WebGPURenderer.html); ~87% browser-support and 30–50% performance-gain figures come from a third-party blog, [utsubo.com](https://www.utsubo.com/blog/threejs-2026-what-changed), read as a community claim, not a primary spec number). You're on r185, past that milestone, so a one-line renderer swap is available. But your bottleneck is geometry size/decode and draw-call count for a mostly-static city, not shader throughput, so the payoff (compute shaders, lower CPU overhead on dense scenes) doesn't target the actual problem. Revisit for GPU-driven culling/compute on instanced trees later — three.js has a `BatchedMesh` + `WebGPURenderer` compute-culling example (`ComputeBatchCulling`, r181) ([threejs-blocks.com](https://www.threejs-blocks.com/docs/ComputeBatchCulling), [Codrops](https://tympanus.net/codrops/2024/10/30/interactive-3d-with-three-js-batchedmesh-and-webgpurenderer/)).

## Ranked list of changes

1. **Bake to glTF/GLB with meshopt (`EXT_meshopt_compression`) + `KHR_mesh_quantization`**, not Draco and not a custom binary format — best fit for ~940 small meshes where decode speed matters more than max compression ratio.
2. **Bundle blocks into region-sized chunk files** (not one file per block per tier) to get compression superadditivity and cut HTTP request count.
3. **Pre-compress every bundle with Brotli** at build time, served with correct `Content-Encoding`, so no runtime CPU cost is paid for compression.
4. **Move trees to `InstancedMesh`** (one instance mesh per tree archetype); stop drawing every tree into the block mesh.
5. **Switch the on-device cache from IndexedDB to Cache API / service worker** for the baked binaries, keeping any structured metadata in IndexedDB if still needed.
6. **Add a runtime capability probe (`detect-gpu` benchmark + WebGL2 `getParameter` limits)** to drive tier/LOD selection instead of trusting `navigator.deviceMemory` or renderer-string sniffing.
7. **Apply voxel-specific vertex packing** (packed position/normal/AO, palette or index-based colour) inside the mesh before glTF export, targeting ≤16 bytes/vertex; benchmark palette-indexed colour specifically since no verified public figure was found for that exact technique.
8. **Leave WebGPU for later**; if pursued, target it for GPU-driven instance culling/compute on the tree/street-furniture instancing layer rather than as a blanket renderer swap.
